# Annotation Validation (LLM as a judge)

`annotations-report.ipynb` checks whether the event annotations generated by our model agree with the matched MEVA reference activities. A Groq-hosted LLM scores each pair, and the results are written to `bronze.annotations_report` in PostgreSQL.

This stage covers **semantic agreement only**. Temporal IoU and spatial IoU are separate stages.

## Where it sits in the pipeline

```
bronze.events  →  matching stage  →  bronze.matched_pairs  →  this notebook  →  bronze.annotations_report
```

The notebook only reads `bronze.matched_pairs`. New events are not evaluated until the matching stage has added them to `matched_pairs`.

## Setup

### 1. Create a `.env` file

The `.env` file holds the credentials and must never be committed. Add it to `.gitignore`:

```gitignore
.env
```

Create `.env` with these variables:

```dotenv
# PostgreSQL (Supabase)
DB_USER=your_db_user
DB_PASSWORD=your_db_password
DB_HOST=your_db_host
DB_PORT=5432
DB_NAME=postgres

# Groq
GROQ_API_KEY=your_groq_api_key
# Optional, defaults to openai/gpt-oss-120b
# GROQ_MODEL=openai/gpt-oss-120b
```

`DB_USER`, `DB_PASSWORD`, `DB_HOST`, `DB_NAME` and `GROQ_API_KEY` are required. `DB_PORT` and `GROQ_MODEL` are optional. Write one `KEY=value` per line, with no quotes or spaces around `=`.

It's worth committing a `.env.example` with the same keys and placeholder values, so teammates know what to fill in.

### 2. Where the notebook looks for credentials

The notebook stops at the first of these that works:

1. Variables already set in the environment (shell, CI).
2. The file named by the `ENV_FILE` environment variable.
3. A `.env` in the working directory or any parent folder.
4. A `.env` found in folders near the working directory (up to 5 levels deep).

A `.env` file is only used if it contains every required variable. If several match, the notebook stops and asks you to set `ENV_FILE`.

- **Locally:** put `.env` next to the notebook, or in the project root.
- **On Kaggle:** upload `.env` as a **private** dataset and attach it to the notebook. The search finds it under `/kaggle/input/...`. Never make that dataset public, because it contains the database password and the API key.

### 3. Dependencies

The first code cell in section 2 installs everything:

```
pandas sqlalchemy psycopg2-binary groq>=0.30 python-dotenv
```

## Running it on new data

1. **Update `matched_pairs`.** Run the matching stage so the new events are in `bronze.matched_pairs`. The coverage check at the end of the notebook shows any events still missing from `matched_pairs`.
2. **Test first (optional).** In section 1, set:
   ```python
   DRY_RUN = True
   MAX_ROWS = 10
   ```
   Then run all cells. Nothing is written to the database. Check the judged rows and the reasons the LLM gave.
3. **Run for real.** In section 1, set:
   ```python
   DRY_RUN = False
   MAX_ROWS = None
   ```
   Then **Run all**. Always re-run from section 1 after changing settings.
4. **Check the output.** It should say `Mode: WRITE`, with `Rows written to database` above 0 and `Failed` at 0.

Only pending pairs are processed: those with no row in `annotations_report` for the current `PROMPT_VERSION`. Re-running is safe, and already judged pairs are never sent to the LLM again.

**If a run stops partway** (Groq's daily limit, a crash, or rows in `failed_df`), run it again later. Everything already written is kept, and the notebook continues with what's left.

### Settings (section 1)

| Setting | Default | Purpose |
|---|---|---|
| `PROMPT_VERSION` | `v2_semantic_judge` | Tags every row. Change it whenever the prompt or rubric changes. |
| `DRY_RUN` | `True` for tests | `True` means nothing is written and the table isn't modified. |
| `MAX_ROWS` | `10` for tests, `None` for real runs | How many rows are sent to the LLM in this run. |
| `BATCH_SIZE` | `20` | Annotations per LLM call. |
| `REASONING_EFFORT` | `low` | Keeps token usage down on the free tier. |
| `MATCH_THRESHOLD` | `0.75` | `llm_match = llm_score >= threshold` |
| `SLEEP_BETWEEN_CALLS` | `2.0` | Seconds between batches, to stay under rate limits. |

### Changing the prompt or rubric

Edit `SYSTEM_PROMPT` in section 7, **change `PROMPT_VERSION`**, then run. Every pair is judged again under the new version, and older versions stay in the table for comparison.

## What gets written

`bronze.annotations_report` contains one row per matched pair per prompt version. Each row has the original `matched_pairs` columns plus:

| Column | Meaning |
|---|---|
| `llm_score` | 1.00 / 0.75 / 0.50 / 0.25 / 0.00. Empty for no-reference rows. |
| `llm_match` | `llm_score >= 0.75` |
| `llm_reason` | The LLM's one-sentence explanation. |
| `eval_status` | `scored`, or `no_reference` (no MEVA activity to compare against, never sent to the LLM). |
| `prompt_version` | Which prompt produced the row. |
| `model` | The Groq model used. |
| `evaluated_at` | When the row was written (UTC). |

On the first write run, the notebook creates the table if it doesn't exist. `(id, prompt_version)` is unique, so a pair can't be written twice under the same version.

## Analysing the results

### Score meanings

| Score | Meaning |
|---|---|
| **1.00** | Same action as a MEVA activity. |
| **0.75** | Same actor or object, and the described behaviour clearly implies a MEVA activity. |
| **0.50** | Consistent with MEVA, but only describes movement, position or appearance, not the MEVA action. |
| **0.25** | A different actor or object, or an unrelated action (but no conflict). |
| **0.00** | Contradicts the MEVA reference. |

The model tends to describe **where things move** ("a white SUV moves left to right"), while MEVA lists **what happens** ("a vehicle stops"). A high share of 0.50 therefore means the descriptions are accurate but aren't phrased as actions. That's a different problem from the model being wrong, which shows up as 0.00.

### In the notebook (section 11)

- **`summary_overview`:** events evaluated, how many were judged, how many had no reference, the mean score and the match rate. The mean and match rate cover judged rows only.
- **`score_distribution`:** how many rows fall on each score.
- **Row-level view:** the judged rows from this run, with reasons.
- **Versions table:** row counts and average score per `prompt_version`.

Always report no-reference events separately. They have nothing to compare against, so they aren't counted as failures.

### Useful SQL

These queries run in the Supabase SQL editor.

Overall results for a version:

```sql
SELECT eval_status,
       COUNT(*)                                        AS rows,
       ROUND(AVG(llm_score)::numeric, 3)               AS avg_score,
       ROUND(AVG(llm_match::int)::numeric, 3)          AS match_rate
FROM bronze.annotations_report
WHERE prompt_version = 'v2_semantic_judge'
GROUP BY eval_status;
```

Score distribution:

```sql
SELECT llm_score, COUNT(*) AS rows
FROM bronze.annotations_report
WHERE prompt_version = 'v2_semantic_judge' AND eval_status = 'scored'
GROUP BY llm_score
ORDER BY llm_score DESC;
```

Results per camera:

```sql
SELECT camera_id,
       COUNT(*)                                  AS judged,
       ROUND(AVG(llm_score)::numeric, 3)         AS avg_score,
       ROUND(AVG(llm_match::int)::numeric, 3)    AS match_rate
FROM bronze.annotations_report
WHERE prompt_version = 'v2_semantic_judge' AND eval_status = 'scored'
GROUP BY camera_id
ORDER BY avg_score;
```

Contradictions, to review by hand:

```sql
SELECT id, event_id, model_event_name, model_description, meva_reference, llm_reason
FROM bronze.annotations_report
WHERE prompt_version = 'v2_semantic_judge' AND llm_score = 0
ORDER BY id;
```

Comparing prompt versions:

```sql
SELECT prompt_version,
       COUNT(*) FILTER (WHERE eval_status = 'scored')          AS judged,
       COUNT(*) FILTER (WHERE eval_status = 'no_reference')    AS no_reference,
       ROUND(AVG(llm_score)::numeric, 3)                       AS avg_score
FROM bronze.annotations_report
GROUP BY prompt_version
ORDER BY prompt_version;
```

Scores from different prompt versions use different rubrics, so compare them with care.

**Spot-check the judge.** Before reporting numbers, read about 10 to 20 rows per score level. Check that the reasons make sense, especially for 0.00 and 1.00.

## Troubleshooting

| Problem | Cause and fix |
|---|---|
| `Missing required environment variables` | No `.env` with all the required keys was found. Check the variable names, or set `ENV_FILE` to the file's path. On Kaggle, attach the private dataset that holds the `.env`. |
| `Pending: 0` | Every pair in `matched_pairs` is already judged for this version. Run the matching stage for new events, or change `PROMPT_VERSION`. |
| `STOPPED: Groq asked to wait ...` | You've hit Groq's daily limit. Run again later; the notebook resumes. |
| Rows in `failed_df` | The LLM gave invalid output even after retries. Those rows stay pending and are retried on the next run. |
| `Response truncated` | Lower `BATCH_SIZE` or raise `MAX_COMPLETION_TOKENS`. |
| `WARNING: columns not in report table` | `matched_pairs` gained a column since the report table was created. Add the column to `annotations_report`, or drop the table and let the notebook recreate it. |

## Known limitation

The notebook tracks which pairs are already judged using `matched_pairs.id`. If the matching stage ever clears and reloads `matched_pairs` rather than adding new rows, the IDs can change. Pairs would then be judged again, and old report rows would point to the wrong pairs. In that case, switch the tracking to `event_id`.
